# Payload 簡易SNS 要件と実装計画

2026年10月29日　対象 React Vite Tailwind CSS と Payload SQLite

目的は、簡易SNSを作りながらPayloadの認証、アクセス制御、データ構造、APIを理解すること。まずローカルで動作させる。Waveは動作確認できる機能の区切り、チケットは個別の作業単位とする。本書は要件と計画を記載し、実装実績は[チケット台帳](../TICKETS.md)で管理する。

## 1 構成と役割

ブラウザーのReact画面 → HTTP REST API → PayloadとNext.js → SQLiteファイル。OktaはWave 4でバックエンドとOIDC連携する。Next.jsはPayloadの実行基盤であり、SNS画面はViteで作る。

PayloadではCollectionが同じ構造のデータ群、Fieldが項目、Relationshipがデータ間の関連を表す。設定からAPIと管理画面が生成される。SNS画面と業務固有の制約は実装する。

開発時はフロント localhost:5173、バックエンド localhost:4310。Viteが /api をバックエンドへプロキシする。管理画面はバックエンドの /admin で開く。Cookie認証を使い、ブラウザーにトークンを永続保存しない。DBに接続するのはバックエンドだけとする。

## 2 機能範囲

ユーザー名とパスワードによるログイン、ログアウト、現在ユーザー取得、テキスト投稿と本人による削除、投稿一覧、ユーザー一覧と詳細、フォローと解除、フォロー中一覧、Oktaログイン、管理者用管理画面を対象とする。閲覧もログイン必須とする。

投稿は空白のみを禁止し、最大500文字とする。文字数はJavaScriptのUTF-16コード単位で判定する。画像、いいね、コメント、DM、通知、投稿編集、フォロー中限定タイムライン、公開デプロイは対象外とする。

### 暫定の運用方針

一般ユーザーの自由登録は設けず、管理者またはローカルseed処理でテストユーザーを用意する。Oktaの既存環境と設定権限は未確認であり、Wave 4着手時に確認する。両方式の自動アカウント統合は行わず、既存の関連付けがなければ別ユーザーとして扱う。

## 3 データ設計

論理上は4つのCollectionを使う。SQLiteの実テーブルにはPayloadの認証セッションなどの補助テーブルも含まれる。DBの実際の構造は生成されたマイグレーションとSQLiteのスキーマで確認する。

### users ユーザー

ID、username、displayName、role、作成日時、更新日時。authを有効にし、パスワードとセッションはPayloadが管理する。usernameは小文字の英数字とアンダースコアで3〜32文字、一意とする。roleはmemberまたはadmin。初回はadmin、alice、bobをseedする。

### posts 投稿

ID、body、author、作成日時、更新日時。authorはusersへの必須関連。投稿者はサーバーが認証ユーザーから設定し、以後変更不可。新着順の一覧とauthorによる絞り込みに合わせてインデックスを検討する。

### follows フォロー

ID、follower、following、作成日時。どちらもusersへの必須関連。followerとfollowingの組み合わせをDBの複合一意制約とする。自己フォローをサーバー側で拒否し、関連の更新は不可。解除後の再フォローは可能。

### auth identities 外部認証の対応

ID、user、issuer、subject、作成日時。issuerとsubjectの組み合わせを一意とする。クライアントからの読み書きを許可しない。Oktaの秘密情報やトークンをプロフィールとして公開しない。

## 4 認証とアクセス制御

ローカル認証はPayload標準のusernameログインを用いる。セッション有効期限は1時間、HttpOnly Cookie、SameSite Laxを基本とし、HTTPS環境ではSecureを有効にする。ログイン失敗の表示、処理中の二重送信防止、再読込での復元、期限切れとログアウトでの未認証状態への遷移を実装する。

一般ユーザーはログイン中のみ公開プロフィールと投稿を閲覧できる。投稿の作成とフォローは本人名義のみ、投稿削除とフォロー解除も本人のものだけとする。一般ユーザーによるユーザー作成、role変更、管理画面利用を禁止する。メールは本人か管理者のみ取得できる。ユーザー削除は一般ユーザーに許可せず、関連データがあるユーザーの削除方針は今後設計する。

APIへ直接アクセスしても同じ権限を適用する。Local APIは既定でアクセス制御を迂回するため、利用者の操作ではoverrideAccess falseと認証ユーザーを明示する。seedのみ管理処理として権限を迂回する。

## 5 Wave の構成

### Wave 1 開発基盤とローカル認証

React Vite Tailwind CSSとPayload SQLiteを起動する。ユーザーを定義し、seed、ログイン、me、ログアウト、管理者制限を実装する。利用者が画面とAPIとDBの役割を説明できる状態を目指す。

### Wave 2 投稿

postsの定義とアクセス制御、投稿フォーム、新着一覧、ページ分割、本人削除を実装する。CollectionからAPIと管理画面が生成される流れを確認する。

### Wave 3 フォロー

followsの定義、重複と自己フォローの禁止、フォローと解除、ユーザー詳細とフォロー中一覧を実装する。1対多と多対多、DB制約を確認する。

### Wave 4 Okta と全体検証

Oktaの利用環境を確認し、OIDCによるログイン、外部ID対応、セッションとログアウトを実装する。実際のOktaで確認し、全機能を通した検証と学習資料を完成させる。

## 6 完了判定の原則

各Waveは、コード作成だけでなく実際のHTTP API、ブラウザー、永続化を確認して完了とする。管理者と一般ユーザー2人を使い、成功する操作と拒否される操作の両方を確認する。テスト用データは本番データと混ぜない。

Wave 1ではログイン成功と失敗、CookieのHttpOnly、meによる復元、ログアウト後の拒否、管理者権限の自己付与防止、メールの秘匿を確認する。Wave 2では他人の投稿の削除と投稿者偽装を拒否する。Wave 3では同時送信でもフォローが重複しないことを確認する。

SQLiteはローカルファイルとして永続化し、DBファイルと秘密情報は配布物に含めない。バージョンはlockfileで固定する。マイグレーションで空のDBを作れることを確認する。将来PostgreSQLへ変更する場合は別途データ移行と再検証を行う。

## 10 Wave 4 チケット

### W4-01 Okta環境と連携方式の確定

依存: ローカル認証の完成とOktaの設定権限。作業: issuer、client ID、秘密情報、redirect URI、割当ユーザーを確認する。Authorization CodeとPKCEを候補としてPayloadセッションへの接続を小さく検証する。

完了条件: 実アカウントで認証結果をサーバーが検証できる。秘密情報をログとフロントへ渡さない。Okta未提供の場合は未完了として記録する。

### W4-02 外部IDとSNSユーザーの対応

依存: W4 01。作業: auth-identities、初回ユーザー作成と再ログイン時の解決、username競合時の初期設定を実装する。

完了条件: issuerとsubjectで同じユーザーを解決する。メール一致だけで統合せず、同時初回ログインでも対応が重複しない。

### W4-03 セッションとログアウト

依存: W4 02。作業: Okta認証後のSNSセッション、カスタム認証、期限切れ、ログアウトを実装する。SNSからのログアウトとOkta側SSOセッションの終了を区別して説明する。

完了条件: 認証結果の署名、issuer、audience、有効期限、state、nonceを検証し、期限切れと改ざんを拒否する。SNSログアウト後に保護APIを利用できない。

### W4-04 全体検証と学習資料

依存: Wave 2 と Wave 3 と W4 03。作業: 両認証方式で投稿とフォローの権限を確認し、最終構成、API、自動生成と追加実装の違いを説明する。

完了条件: 実際のOktaログインを含めて一連の操作が再現できる。モックだけの状態を完了にしない。

## 12 Wave 3で確認した実装方針

- フォローは独立Collectionとし、`follower`と`following`の複合一意制約をマイグレーションで作成。
- 管理者も他人のフォローを解除できない。更新は禁止し、解除後の新規作成を許可。
- 関係の閲覧はログイン必須。フロントは必要なページと対象IDの関係だけ取得し、全ユーザー・全関係の一括取得を避ける。
- 自分のフォロー中とユーザー一覧は20件ずつ。詳細画面は対象ユーザーの投稿を新着順に取得。
- 同時作成と他タブの状態変更はDB制約と再取得で扱う。フォロー中限定タイムラインは引き続き対象外。
- 完了した検証と制限は[チケット台帳](../TICKETS.md)を参照。

## 13 Wave 4の具体化（実環境確認待ち）

詳細は[Okta設定と認証設計](okta-setup.md)を参照。外部ID対応に加え、内部専用の `oidc-sessions` と `oidc-flows` を追加する。SNSログアウトを提供し、Okta側のSSO終了は行わない。既存SNSセッションへのOkta側無効化の即時反映は対象外で、1時間の期限を設ける。

Okta用usernameは外部IDのハッシュとランダムな接尾辞から生成し、既存usernameとの競合時はトランザクションをロールバックして再生成する。ユーザーに任意usernameを設定させる初期画面は今回追加せず、表示名はOktaのnameを利用する。メール一致による自動統合は禁止を維持する。

モックOIDCとPayload RESTハンドラーによる検証は実施済みだが、実Oktaでのログインと画面操作が成功するまでW4の完了条件を満たしたとは扱わない。
